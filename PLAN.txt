PLAN
Dataform migration for the reports.revenue_daily route
Project: task2_estate/dataform

task2_estate/dataform is the implementation of this design. It compiles
to 13 targets: 3 declarations, 6 tables, and 4 assertions. No scheduled
query has been disabled, and no production table has been rebuilt.
AUDIT.txt, COST.txt, and the task2_estate source files are unchanged.

1. What this migration covers
The route is migration_scope for the table name revenue_daily: ancestors of
table:reports.revenue_daily, both current writers, and scheduled-query
descendants. Dashboard and ad-hoc consumers sit on the downstream lineage.
Queries that only share a raw or staging source are outside the route.
shared_source_siblings returns 54 of those queries. They stay on Scheduled
Queries.

Graph slice (10 scheduled queries):
  sq_0101  staging.stg_payments
  sq_0102  staging.stg_subscriptions
  sq_0103  staging.stg_fx_daily
  sq_0104  reports.revenue_daily
  sq_0105  reports.revenue_daily
  sq_0106  reports.revenue_by_region
  sq_0111  reports.exec_kpi_daily
  sq_0112  reports.kpi_snapshot
  sq_5001  marts.revenue_unified
  sq_5005  marts.exec_kpi_v2
Sources: raw.payments, raw.subscriptions, raw.fx_rates.

sq_0105 is on the graph slice because it writes reports.revenue_daily today.
It is not a Dataform action. Section 4 explains why. The three KPI queries
stay in the design and are blocked on column contracts. Section 3 lists them.

2. Action count
The design contains 16 Dataform actions:

  3 source declarations
  6 transformations that can be implemented from the current SQL
  3 downstream transformations blocked on column contracts
  4 uniqueness assertions

13 of the 16 are implemented under task2_estate/dataform and compile.
The other 3 are not built. No placeholder SQLX was added for them.

Blocked until the column contract is resolved:
  reports.exec_kpi_daily   sq_0111
  reports.kpi_snapshot     sq_0112
  marts.exec_kpi_v2        sq_5005

sq_0111 reads payment_date from reports.revenue_by_region. The Dataform
revenue_by_region action is sq_0106, which renames payment_date to
report_date and drops it with EXCEPT. sq_5005 reads payment_date from
reports.exec_kpi_daily. sq_0111's own SELECT would rename that column to
report_date, so the name sq_5005 filters is not on that projection.
sq_0112 reads metric_name and metric_value from reports.exec_kpi_daily.
Neither name appears in sq_0111. It also reads snapshot_date from its own
destination (OP-SELF-READ-sq_0112).

schemas.json does not describe these four tables. table_catalog.csv has
counts only: revenue_by_region 17, exec_kpi_daily 8, kpi_snapshot 12,
exec_kpi_v2 13. Those counts do not match the SELECT lists in the files.
run_history.csv records SUCCEEDED for sq_0111, sq_0112, and sq_5005 on
all 90 daily rows, and the error_message column is empty. A succeeded
row does not name the columns the job read. Replacing payment_date with
report_date, or deriving metric_name and metric_value from the revenue
columns, would publish a contract the files do not contain. The three
queries stay on their scheduled configs. sq_0105 is also not a Dataform
action: it is the second writer of reports.revenue_daily, and section 4
keeps sq_0104 as the only Dataform writer.

4. reports.revenue_daily has one Dataform writer
sq_0104 and sq_0105 both target reports.revenue_daily today. The statements
are different.

sq_0104, scheduled_queries/sq_0104__reports__revenue_daily.sql
  Comment "Revenue daily (main)", owner comment olena.kravets@acme.co.
  every day 03:10 Europe/Kyiv, WRITE_TRUNCATE, partitioning_field empty.
  Reads staging.stg_payments, staging.stg_subscriptions, staging.stg_fx_daily.
  Dedupes payments by payment_id on updated_at, ingested_at.
  Drops subscriptions where COALESCE(is_test, FALSE).
  Inner-joins subscription_id. Left-joins FX on rate_date and currency.
  Keeps status = 'settled' and DATE(created_at) >= CURRENT_DATE() - 3 days.
  GROUP BY payment_date, country_code, region, tier, billing_period_days.
  Columns: payment_date, country_code, region, tier, billing_period_days,
  payments, payers, revenue_usd.
  region is the CASE on country_code in that file. revenue_usd is
  amount_minor / 100.0 * COALESCE(rate_to_usd, last_known_rate, 1.0).

sq_0105, scheduled_queries/sq_0105__reports__revenue_daily.sql
  Comment "Revenue daily hourly topup", owner comment dmytro.shevchuk@acme.co.
  every 1 hours Europe/Kyiv, WRITE_APPEND, partitioning_field empty.
  Reads raw.payments only. No subscription join, no FX, no settled filter.
  Window is DATE(created_at) for 1 day.
  Grain: attempt_hour, processor, status, attempt_no.
  Columns: attempt_hour, processor, status, attempt_no, attempts, users,
  amount_local, settle_rate.
  amount_local is SUM(amount_minor) / 100.0, with no FX conversion.

sq_0106 and sq_5001 select payment_date and region from reports.revenue_daily.
sq_0105 projects neither column (CR-COLUMN-WRITER-CONFLICT, needs_verification).
The finding shows the files disagree. It does not show which schema the live
table has.

sq_0114 writes the same statement text as sq_0105, after comment and
whitespace removal (MN-REPEATED-SQL-sq_0105-sq_0114), to
reports.payment_settle_hourly. That config is hourly WRITE_APPEND and is not
on this route. Recorded consumers are looker/funnel_explorer and
sheets/cfo_weekly. sq_0114 stays a Scheduled Query. Pointing a Dataform
action at payment_settle_hourly would add a second writer of that hourly grain.

The Dataform table reports.revenue_daily is the sq_0104 statement only.
sq_0105 is not implemented as a table, an incremental, or an append into
that table. AUDIT left both writers in the registry until an owner chose
one. This plan is that choice for the Dataform slice: the daily settled
contract is what the downstream files read. The hourly attempt grain stays
with sq_0114. Disabling sq_0105 in the live project is still an owner action
during cutover. This repository does not disable it.

5. Facts that the SQLX has to respect
All ten configs on the graph slice are ENABLED, disabled false, timezone
Europe/Kyiv, dataset region eu, partitioning_field empty.

schemas.json describes raw.payments (15 columns), raw.subscriptions (19),
and raw.fx_rates (rate_date, currency, rate_to_usd). It has no staging,
reports, or marts tables. table_catalog.csv partitions raw.payments by
_PARTITIONTIME. raw.subscriptions and raw.fx_rates have an empty
partition_column.

Catalog column counts disagree with the outermost SELECT lists
(CR-SCHEMA-COUNT, indicated). On this route: sq_0101 SQL 15 vs catalog 8,
sq_0102 SQL 19 vs catalog 13, sq_0103 SQL 4 vs catalog 17, sq_0104 SQL 8 vs
catalog 10. The catalog field is a count, not a name list. The migration
keeps the SQL lists. It does not add columns to match the catalog, and it
does not add a _PARTITIONTIME predicate where the SQL filters DATE(created_at)
or DATE(updated_at). sq_0101 is in OP-PARTITION-FILTER (needs_verification)
for that reason.

reports.revenue_daily in the catalog snapshot has 249,576,926 rows and 10
columns. The sq_0104 file is an 8-column aggregate limited to 3 days, then
WRITE_TRUNCATE. Those two descriptions do not match. CR-SHORT-LOOKBACK-sq_0104
(indicated) records that the 3-day bound does not prove what the live table
retains, and that sq_0106 filters 400 days and sq_5001 filters 730 days.
The migration leaves the 3-day predicate in place. A longer retained history
would be a different table than the current truncate writes.

CURRENT_DATE() stays unqualified except in sq_0111, which passes
"Europe/Kyiv". The transfer timezone is not written into the other calls.

6. Source-to-target mapping
Schedules below are the transfer configs being replaced for that destination.
Dataform runs the ready actions in ref() order, not on those clocks.
Materialization for each WRITE_TRUNCATE query is a Dataform table: the run
replaces the table with the SELECT result. No partition decorator is added.

  One row per payment_id. ROW_NUMBER is ordered by updated_at DESC,
  ingested_at DESC. The 3-day filter on DATE(created_at) is inside the
  window subquery, so an older payment_id does not compete.
  Columns, in file order: payment_id, order_id, subscription_id, user_id,
  amount_minor, currency, status, processor, attempt_no, is_rebill,

  maria.voloshyna@acme.co, and sq_0104.

6.2 staging.stg_subscriptions, sq_0102
  every day 03:00, WRITE_TRUNCATE. Depends on raw.subscriptions.
  ROW_NUMBER partitions by subscription_id, keeps _rn = 1, and has no
  ORDER BY (CR-ROW-NUMBER-NO-ORDER, confirmed; sq_3027 is the other hit and
  is outside this route). The result has one row per subscription_id in the
  window. Which source row survives is not determined by the SQL. The
  migration does not add an ORDER BY.
  Filter: DATE(updated_at) for 7 days, inside the window subquery.
  Columns: the 19 names in the outer SELECT, subscription_id through
  ingested_at.
  Other readers: metabase/support_console and sq_0104.

  Columns: rate_date, currency, rate_to_usd, last_known_rate.

7. Assertions
The four assertions check uniqueness at the grain the SQL already produces.
A uniqueKey check does not prove that a key column is non-null. Dataform
nonNull is a separate assertion. It is not in this set. Adding it would need
evidence that a null is invalid, and several of these columns can be null
in the current SQL: country_code, tier, and billing_period_days come from
the subscription row; payment_date is DATE(created_at); rate_to_usd and
last_known_rate come from a left join. payment_id and subscription_id are
the partition keys of ROW_NUMBER. A null key would collapse to one output
row and still pass a uniqueness check. That is not a non-null check.

  assert_stg_payments_payment_id
    Grain: one row per payment_id after the ordered ROW_NUMBER.
    Assertion: uniqueKey payment_id.
  assert_stg_subscriptions_subscription_id
    Grain: one row per subscription_id after the unordered ROW_NUMBER.
    Assertion: uniqueKey subscription_id.
    This counts rows. It does not choose which source row won.
  assert_stg_fx_daily_rate_date_currency
    Grain: one row per rate_date, currency on the date spine.
    Assertion: uniqueKey rate_date, currency.
  assert_revenue_daily_grain
    Grain: the sq_0104 GROUP BY, which is payment_date, country_code,
    region, tier, billing_period_days. region stays in the key because it
    is one of the grouped expressions, even though the CASE derives it from
    country_code.
    Assertion: uniqueKey on those five columns.

No assertion is defined for exec_kpi_daily, kpi_snapshot, or exec_kpi_v2.
An assertion on metric_name would name a column the writer file does not
project.

02:40, 03:00, 03:10, 04:00, 05:00, 06:00, 06:30, and 06:52 are not copied
as eight schedules. The time of day is still open: the files do not say
when the raw tables finish landing, and those tables are declarations.

removes them as a scheduling mechanism:
  OP-SCHEDULE-OVERLAP-sq_0101-sq_0104, confirmed, 90 of 90 paired reader

11. Cutover and rollback
None of the production switch below has been done. This lab has no
warehouse, so dataform run cannot be compared with production here.
make compile is the check on the 13 files that exist. It does not prove
row-level equivalence.

Validation happens in an isolated dataset or project, while the production
Scheduled Queries keep writing the production table names.

  1. The 13 actions are already in task2_estate/dataform. Point an isolated
     run at a dataset or project that production consumers do not read.
  2. Compile the project (make compile). Fix compile errors before any
     write to production names.
  3. Where warehouse access exists, run the isolated workflow and compare
     it with the legacy output for the same as-of date: column names and
     types, row counts, the four unique keys, and the financial aggregates
     the SQL already defines (payments, payers, revenue_usd, and the
     pass-through of those measures). Compare against the legacy query
     result, not against table_catalog.csv row_count.
  4. Check that consumers of the production names still match the published
     columns. The ready actions keep those projections. The blocked KPI
     tables are not switched.
  5. Get owner approval that sq_0104 is the canonical definition of
     reports.revenue_daily, and that sq_0105 will stop appending to it.
  6. Disable the legacy writer of each table before the Dataform action
     for that same table is enabled against the production name.
     Order for the ready slice: disable sq_0105 so it can no longer append
     to reports.revenue_daily; then disable sq_0101, sq_0102, sq_0103,
     sq_0104, sq_0106, and sq_5001. Leave sq_0114 enabled on
     reports.payment_settle_hourly. Leave sq_0111, sq_0112, and sq_5005
     enabled until their own SQLX exists.
  7. Confirm the disabled configs are not mid-run, then enable the
     revenue_daily Dataform workflow against the production datasets.
  8. Watch the run, the four assertions, and the consumers in section 10.
     sq_0109 and the other stg_fx_daily readers are part of that watch,
     because they still query the table Dataform will publish.

A production table is never written by a Scheduled Query and a Dataform
action in the same period. The isolated run is the only overlap allowed,
and it writes somewhere else.

Rollback, if the isolated run is wrong: leave every production schedule
as it is, and discard the isolated output. Production was not switched.

Rollback, if production has already switched: disable the Dataform
workflow and wait until no Dataform run is still writing. Only then
re-enable the scheduled configs that were turned off (sq_0101, sq_0102,
sq_0103, sq_0104, sq_0106, sq_5001). Re-enable sq_0105 only with a separate
owner decision; turning it back on restores the second writer of
reports.revenue_daily, and it still must not run while the Dataform
revenue_daily action is enabled. sq_0114 is left running in either
direction. Tables are not dropped. This repo has no backup of the previous
table contents. The next successful legacy run rebuilds the table from
that query's SQL, which for these WRITE_TRUNCATE jobs is the query result,
not a restore of the catalog snapshot.

sq_0111, sq_0112, and sq_5005 are outside this switch. Their rollback is
"they were never moved."

12. Equivalence
With no warehouse, equivalence for the 13 implemented actions is file
equivalence plus compilation. The SELECT lists, filters, joins, CASE, and
window frames of sq_0101, sq_0102, sq_0103, sq_0104, sq_0106, and sq_5001
are copied. Only the table references change, to Dataform refs. Dataset
and table names stay. The 3, 7, 400, and 730 day intervals stay. Empty
partitioning_field stays empty. sqlglot comparison of the compiled SQL
with those six files is a text check. It is not a comparison of rows,
revenue_usd, or assertion results. No BigQuery job was run.

sq_0105 has no Dataform equivalent. The hourly attempt grain continues as
sq_0114. sq_0111, sq_0112, and sq_5005 have no SQLX and no equivalence
claim. Their column contracts are still the open questions in section 14.

13. Cost
COST.txt prices the 10-query graph route at 0.9256 TiB/day and $5.79/day,
including sq_0105 at $1.7748/day. That is observed query cost for the
slice, not a saving from this migration.

of $3.4362/day for the two named queries. Associated spend is not a saving
from dropping one copy. These amounts are not additive with the estate
total or with the hypothetical hourly-collapse scenario.

15. Migration order
The order followed is the dependency order, and each step compiles on
its own:

  1. Declare raw.payments, raw.subscriptions, and raw.fx_rates. Dataform
     does not build these tables.
  2. staging.stg_payments, staging.stg_subscriptions, staging.stg_fx_daily
     from sq_0101, sq_0102, and sq_0103.
  3. reports.revenue_daily from sq_0104, then reports.revenue_by_region
     (sq_0106) and marts.revenue_unified (sq_5001). Both readers depend
     on revenue_daily, not on each other.
  4. The four uniqueness assertions, after the tables they check.

sq_0105, sq_0111, sq_0112, and sq_5005 have no SQLX. make compile exits
0. dataform run is not expected to succeed in this lab.

No shared macro was added under includes/. The region CASE is only in
sq_0104, so it stays in that statement. Repeated SQL outside this route
was left on the scheduled queries instead of being folded into a helper.

16. How this was done
tools/ loads the estate, parses SQL with sqlglot, builds the dependency
graph, writes AUDIT.txt, and writes COST.txt from run_history.csv.
Those files are regenerated by the commands in README.txt. The numbers
are the tool output.
